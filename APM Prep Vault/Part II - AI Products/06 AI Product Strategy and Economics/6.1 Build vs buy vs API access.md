# 6.1 Build vs buy vs API access
> Start with a vendor API to learn what users want, then move down the stack only when cost, control or data needs justify it.

## Concept
There are three broad sourcing options for model capability:

| Option | What you do | Pros | Cons |
|---|---|---|---|
| Build (train your own) | Pretrain or heavily train a model | Full control, possible moat | Very expensive, needs scarce talent and data |
| Host an open-weight model | Fine-tune and run an open-weight model (e.g. Llama, Mistral, Qwen, DeepSeek families) on your infra or a cloud | Lower marginal cost at steady high volume, data stays in your VPC, no surprise deprecations | You own serving, scaling, evals and upgrades; usually behind the frontier on hardest tasks |
| API access | Call a hosted model (OpenAI, Anthropic, Google, etc.), directly or via a cloud (Azure, AWS Bedrock, Google Vertex) | Fastest, best-in-class quality, no infra, prices tend to fall over time | Vendor model changes and deprecations, data-handling terms, rate limits, less control |

Decision factors for a PM:
- **Differentiation:** Is the model itself the product, or is it a component? Most products are the latter.
- **Data sensitivity:** Regulated or confidential data may force self-hosting or a private deployment.
- **Volume and unit cost:** API cost is linear in usage; self-hosting has a large fixed cost (GPUs, engineers) and only becomes cheaper at high, steady utilisation. Because API prices for a given capability have fallen fast, the break-even point keeps moving; re-check it yearly.
- **Quality bar:** If a frontier API meets the eval bar, the premium for building is rarely justified.
- **Team capability:** Serving and evaluating models is an ongoing platform cost, not a one-off project.

The real-world default in 2025-26 is a mix: an API for hard, low-volume tasks and a small or open model for narrow, high-volume ones, behind a thin routing layer.

A common path: prototype on an API, measure quality and usage with evals, then consider routing high-volume, narrow tasks to a smaller or fine-tuned model. Keep the abstraction layer thin so you can switch vendors.

## Real-world examples
- **GitHub Copilot** - launched on OpenAI models; since late 2024 it has let users choose models from several vendors (including Anthropic and Google). GitHub owns the IDE integration and product experience, so the model is a swappable component (buy-and-integrate).
- **Duolingo Max** - launched in 2023 on GPT-4 for features such as "Explain my answer" and roleplay, while Duolingo focused on pedagogy and UX.
- **Sarvam AI (India)** - builds its own models for Indian languages and voice, and in April 2025 was selected under the government's IndiaAI Mission to build a sovereign foundation model: the build path, justified by language coverage and sovereignty rather than by cost.
- **Freshworks Freddy AI (India-founded SaaS)** - generative features such as reply suggestions and ticket summaries built on third-party models combined with Freshworks' own customer data: "buy the model, own the workflow".
- **BloombergGPT (2023)** - Bloomberg trained its own 50-billion-parameter finance model. Later evaluations showed general frontier models matching or beating it on many finance tasks, a cautionary tale for training from scratch.

## Practice questions
1. A healthtech startup wants AI summaries of patient notes. Build, host, or API? What would change your answer?
   - Outline: data residency and compliance push toward private hosting or an API covered by a health-data agreement (in the US, a HIPAA Business Associate Agreement; in India, DPDP-compliant processor terms); start with the API for quality, measure, then decide on hosting.
2. Your API cost doubled after a vendor price change. What do you do in the next two weeks?
   - Outline: check per-task cost, route simple requests to a cheaper model, cache, and set a fallback to an open model.
3. When would you tell leadership not to train a foundation model?
   - Outline: almost always, unless the model itself is the product, you have unique data at scale, a gap that APIs and open models cannot fill (language, sovereignty, on-device), and the budget to keep retraining as the frontier moves. Otherwise fine-tune or prompt an existing model and invest in workflow and data.
4. How do you keep vendor lock-in low without over-engineering?
   - Outline: one internal interface for model calls, prompts and evals stored outside vendor tools, the eval suite as the switching test, and a tested fallback model. Avoid building an abstraction over every vendor feature.
